# 🧭 Памятка: FSD в этом проекте (Next.js App Router)

## Слои (сверху вниз, импорты — только вниз)

```
app          → провайдеры, глобальные стили, слой инициализации приложения
views/pages  → композиция виджетов в конкретный экран
widgets      → крупные самостоятельные блоки UI (шапка, сайдбар, карточка+фильтры)
features     → пользовательские сценарии (поиск, добавить в избранное, сменить тему)
entities     → бизнес-сущности (character, episode, location) — данные + их отображение
shared       → переиспользуемая инфраструктура, ничего не знает о домене
```

Правило: слой может импортировать только нижележащие слои. `entities` не знает про `features`, `shared` не знает ни про что доменное.

## ⚠️ Конфликт имён: Next `app/` vs FSD `app`

У Next есть каталог `app/` — это роутинг (`page.tsx`, `layout.tsx`). У FSD есть слой `app` — провайдеры и глобальная инициализация. Это разные вещи.

Решение в проекте:
- `src/app/**` — **только** Next-роутинг. Файлы тонкие: импортируют компонент из `views` и рендерят его, передавая `params`/`searchParams`.
- `src/views/**` (или `pages`, если не путается с Next `pages/`) — FSD-слой композиции экранов.
- Провайдеры (`Providers` с `QueryClientProvider` и т.п.) — можно класть прямо в `src/app/providers.tsx`, это законная часть Next-роутинга, не нужно тащить под отдельный FSD-слой `app`.

## Сегменты внутри слайса

Каждый слайс (`entities/character`, `features/search-character`, ...) делится на:

| Сегмент | Что кладём |
|---|---|
| `model/` | типы, схемы валидации, стор/контекст, редьюсеры |
| `api/` | функции запросов, query-фабрики (`queryOptions`) |
| `ui/` | React-компоненты этого слайса |
| `lib/` | внутренние хелперы слайса (не переиспользуемые снаружи) |
| `index.ts` | **публичный API** — единственная точка входа для остальных слоёв |

## 🔑 Главное правило: публичный API

Импортировать чужой слайс — **только** через его `index.ts` (`@/entities/character`), никогда напрямую в сегмент (`@/entities/character/api/api`).

```ts
// ✅ снаружи слайса
import { getCharacters, Character } from '@/entities/character'

// ❌ снаружи слайса — минуя публичный API
import { getCharacters } from '@/entities/character/api/api'
```

Внутри своего же слайса — наоборот, импортируем напрямую по относительным путям, а не через собственный `index.ts` (иначе получаем цикл `index → api → index`):

```ts
// entities/character/api/api.ts
// ✅ внутри слайса — относительный путь
import { Character } from '../model/type'

// ❌ внутри слайса — импорт из своего же публичного API
import { Character } from '@/entities/character'
```

## Where does X go? (шпаргалка по типу кода)

- **Тип ответа API / доменная сущность** → `entities/<сущность>/model/type.ts`
- **Функция запроса к серверу** (`getCharacters`, `getCharacter`) → `entities/<сущность>/api/*`
- **`queryOptions`-фабрика** (TanStack Query) → рядом, `entities/<сущность>/api/queries.ts`
- **Базовый fetch-клиент, `ApiError`, общие типы вроде `PaginatedResponse<T>`** → `shared/api`
- **Карточка персонажа (просто отображение)** → `entities/character/ui`
- **Поиск с debounce, фильтры, кнопка «в избранное»** (сценарий, есть логика/состояние) → `features/*`
- **Блок «список персонажей + фильтры сверху»** (композиция нескольких features/entities) → `widgets/*`
- **Экран `/characters`** (собирает виджеты в макет) → `views/characters`
- **Файл роутинга** `src/app/characters/page.tsx` → импортирует `views/characters`, больше ничего не делает
- **Хук на все приложение, утилита без домена** (`cn()`, `useDebounce`) → `shared/lib`
- **UI-кит без бизнес-логики** (Button, Input) → `shared/ui`

## Как отличить `entities` от `features`

Вопрос-тест: *«Есть ли здесь пользовательский сценарий/действие, а не просто данные»?*
- «Персонаж и его поля» → сущность → `entities`.
- «Пользователь ищет персонажа по имени» → сценарий → `features/search-character`.
- «Пользователь добавляет персонажа в избранное» → сценарий → `features/toggle-favorite`, но сам список избранного (что это, как хранится) может быть `entities/favorite` или частью `entities/character`, если избранное — просто флаг у персонажа.

## Тесты и линт архитектуры

- Соблюдение слоёв и публичного API проверяется линтером — см. обсуждение `no-restricted-imports` / `eslint-plugin-boundaries` / `steiger` (этап CI в PLAN.md).
- Компоненты слайса тестируются рядом с ним же (например, `entities/character/ui/CharacterCard.test.tsx`), а не в отдельном параллельном дереве.
